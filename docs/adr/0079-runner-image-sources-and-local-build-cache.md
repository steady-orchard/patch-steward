# ADR-0079: Runner image sources, digest identity, and the local build cache

- Status: accepted
- Date: 2026-09-28
- Deciders: project owner
- Source: `docs/architecture.md` §6.7, §8, §12; `docs/processes.md` SP17; `docs/user-manual/configuration.md` "Runner"

## Context and Problem Statement

The policy schema already allowed a `registry` reference or a `dockerfile` path under `.github/patch-steward/runner/`, but how images are obtained, identified, built, and cached was an open implementation decision (architecture §15, container image strategy and build caching). Evidence must identify the environment that produced a result, and a pull request must not be able to change the environment used to screen it.

## Considered Options

- Only the two policy sources: a public registry image resolved to its digest at pull, or a Dockerfile under `.github/patch-steward/runner/` built from the trusted policy revision and cached locally by its tree id
- Images generated by the steward from policy-declared toolchain lists
- Registry images used by tag, with registry credentials for private images

## Decision Outcome

Chosen option: "Only the two policy sources: a public registry image resolved to its digest at pull, or a Dockerfile under `.github/patch-steward/runner/` built from the trusted policy revision and cached locally by its tree id", because the policy then pins the one image definition and the evidence records an immutable identity. Generated images were rejected because they are a second image definition the policy does not pin and would make the environment depend on steward code. Use by tag was rejected because a tag can move, so evidence would not identify the environment. Registry credentials were rejected because they would put a secret on the execution path.

With `source: registry`, a public image is pulled with `--platform linux/amd64` within `limits.execution.image_pull_seconds`. A tag is resolved to the repository digest at pull; a reference pinned with `@sha256:` must equal it, else `runner.image-digest-mismatch`. Containers then run as `<repository>@<digest>`, never by tag, and the digest is recorded as environment identity. The steward never passes, stores, or configures registry credentials and leaves the host runtime's own configuration (context, login) unchanged; private images are unsupported.

With `source: dockerfile`, the build context is the regular files of the `.github/patch-steward/runner/` subtree at the loaded policy revision, read from git objects (or GitHub tree and blob reads by tree id), never from a working tree. A symlink or gitlink there is `runner.build-context-invalid`. The context archive is at most `limits.execution.build_context_bytes`. The image is built with `--platform linux/amd64`, steward labels, and the tag `patch-steward-runner:<runner tree id>` (the git tree id of `runner/`), with no build arguments, secrets, or SSH, on the runtime's default build network, within `limits.execution.image_build_seconds`. The bounded, redacted build output is stored as the run log `logs/image-build.txt`.

An existing image tagged `patch-steward-runner:<runner tree id>` with the matching runner-tree label is reused and recorded `cached: true`. The steward never prunes images; remove one manually, for example `docker image rm patch-steward-runner:<runner tree id>` (or `podman image rm ...`). Image size is checked after pull or build against `limits.execution.image_bytes` (`runner.image-too-large`; the image stays in the local cache). Under `--policy-file` (revision `local:<sha256>`, no git tree) a `dockerfile` image is unavailable (`runner.image-source-unavailable`); registry images work. Version 1 never generates images from toolchain lists.

### Consequences

- The digest (or local image id) is the recorded environment identity.
- Builds read `runner/` from git objects at the policy revision only, so a pull request cannot change the image used to screen it.
- Cache hits are recorded as `cached: true`, and images are never pruned; removal is manual.
- A `dockerfile` image under `--policy-file` ends `runner.image-source-unavailable`.
- Image size is checked after pull or build, and the build log is stored redacted as `logs/image-build.txt`.
- Under Podman an image must leave `/work` absent or empty ([ADR-0085](0085-container-hardening-profile-and-checkout-delivery.md)), so the runtime choice can decide whether a policy's image is usable.
- Image caching for GitHub-hosted runs is not part of this decision and is not implemented.
- The architecture no longer lists the container image strategy as open.
